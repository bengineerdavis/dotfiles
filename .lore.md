* **Copier is one-directional: template→subproject only; answers file is the update memory**: Copier flows template → subproject only: \`copier copy\` renders; \`copier update\` re-renders at a newer template ref; nothing flows project → template. The answers file (\_src\_path + \_commit + answers \[\[01a1d838-19c3-7a0c-8387-cd692ae70e6b]]) is the memory that makes update safe and already serves as each layer's identity — what stacks lacked was never which templates but what each did to shared files, which is why CC-6 (cross-layer resolution report) is the real gap and the stack file is more derivative than presented. <!-- lore:01a1d855-dfe6-7f32-a0e5-1df19996d306 -->
* **copier-cat composition engine: one 5-stage pipeline, per-format adapters**: copier-cat composition architecture: ONE process for every file type with small format-specific adapters — neither a universal merge algorithm nor per-format systems. Shared 5-stage pipeline: PARSE (format-specific) → IDENTIFY chunks (shared) → MERGE by identity + ordering (shared) → REPORT every decision (shared) → SERIALIZE once (format-specific). Structured formats (TOML/YAML/JSON) are trees: chunks by path, additive across paths, explicit rule on same-path collision; arrays need identity rules (e.g. \`id\`) or append/replace/dedupe diverge. Markdown: named regions \`\<!-- cc:begin name -->\`…\`\<!-- cc:end name -->\` (heading-path IDs less reliable). Plain text: whole-file replace / ordered concatenation / line merge (.gitignore = ordered line set); arbitrary text may be uncomposable (\`enable\_feature false\` vs \`true\`) — no reliable identity → whole-file ownership or review, never an invented merge; unsupported overlap fails visibly, never silently picks a winner. Binary: never text-merge. Two tiers: structured files join the clean data path; a layer shipping a literal fragment (APT's mise.toml today) works standalone but can't join tier one — converting it is the main migration cost.

* **copier-cat PRINCIPLES.md consent boundary: --yes scopes, writes need consent at the action**: copier-cat PRINCIPLES.md (constitution): deterministic machinery first; AI may classify and propose but is never the merge engine; all output reviewable; no project modification, overwrite, publication, or source-template patch lands without explicit human consent AT the action. ccc init: automation never prompts, and missing config never selects a default stack; never force-reset or directly edit managed OpenCode config. Assembly spec: \`--yes\` approves ONLY the displayed new-destination write — not agent installation, source-template changes, publishing, telemetry, or updates to an existing project; cancellation leaves no approved destination. Planning/inspection/preview may run automatically; consequential actions need explicit review at the action — a conversational request is not blanket permission for unrelated writes. Why: agent loops must never convert exploration into consequential writes \[\[01a1db58-c1d6-7fcb-9f8f-d30f9ea83e13]].

<!-- lore:01a1d829-2c14-74a5-9a6e-28b918dc676a -->
* **copier-cat scope: single-template copier workflows never need it; stacks only**: A single Copier template is self-describing (questions, files, answers file), so \`copier copy\`/\`copier update\` work with zero copier-cat involvement forever — the lock-in guarantee holds. copier-cat exists ONLY for the stack case: two templates rendering to one destination and claiming the same file (e.g. python-project-template + agentic-project-template both claiming mise.toml). Copier itself has no concept of two templates owning one file — a missing concept in the problem space, not a missing copier-cat feature. Adding copier-cat to single-template flows solves a non-problem. Design thread: \[\[01a1d13b-c05f-7589-a7af-a2d3fe1ba079]].

* **copier-cat CC-7: shared-file content as data keys; copier -d full-value-replace gotcha; merge registry**: For zero-conflict composition, a layer must expose shared-file content as DATA (template variables with structured defaults), not literal fragments — e.g. \`mise\_tools: {type: yaml, default: {roborev: latest}}\`; cc deep-merges per key before copier renders. Free-text files keep marked sections with by-name identity (CC-6 residue). Motivating gotcha (probe-verified 2026-11-13): \`copier -d 'tools={...}'\` replaces the ENTIRE variable value, silently wiping sibling keys — it reads as a per-key patch but isn't. Fix: deep-merge all layers per key and pass ONE complete --data-file, never two per-layer --data calls. Registry.merge(path, base, ours, theirs) -> MergeResult: dispatch is content/path-aware, first merger whose accepts() wins, git merge-file is the fallback; adopt supplies the empty tree as base. Tests pin TOML/YAML named-lists merge-by-name. CC-7 therefore composes structured render results from isolated native renders instead of merging data pre-render.

* **copier-cat CC-9 slot cardinality: numeric min/max fields, not exactly-one/optional-one/any vocabulary**: CC-9 slot cardinality design (2026-11-13): user REJECTED the exactly-one/optional-one/any vocabulary — cardinality must be numeric expressions. Chose \`min\`/\`max\` integer fields over raw YAML keys (\`>=1\`, \`exactly: 1\`) because min/max is widely understood in schema validation and covers every case (min:1/max:1 = exactly one; min:0/max:1 = zero or one; min:1 no max = at least one; min:0 no max = unbounded; min:2/max:4 = range) without inventing a mini-language or needing separate fields per case; \`>=1\` is readable but awkward as a structured field. Slot schema: foundation (role: base, min: 1, max: 1), application (role: specialization, min: 0, max: 1), overlays (role: overlay, min: 0, no max = unbounded). Required templates stay SEPARATE from cardinality: the requires block names slot + template (e.g. slot: foundation, template: opencode-overlay) — 'must be among them' is a requirement, not a count. Supersedes the vocabulary decision recorded earlier in CC-9. Related: CC-7 two-problem split \[\[01a1d855-dfd0-7a99-9d02-602c72f4923b]].
