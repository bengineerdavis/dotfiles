<!-- lore:01a1d89d-27d7-733f-9eb1-79d6568a7d80 -->
* **Copier is one-directional: template→subproject only; answers file is the update memory**: Copier flows template → subproject only: \`copier copy\` renders; \`copier update\` re-renders at a newer template ref; nothing flows project → template. The answers file (\_src\_path + \_commit + answers \[\[01a1d838-19c3-7a0c-8387-cd692ae70e6b]]) is the memory that makes update safe and already serves as each layer's identity — what stacks lacked was never which templates but what each did to shared files, which is why CC-6 (cross-layer resolution report) is the real gap and the stack file is more derivative than presented. Pushing project fixes upstream is copier-cat's separate 'phone home' (C2) ambition — keep it out of stack-composition work. Under stacks, render-derived ownership can't attribute an edit to a layer (python pin → base; roborev pin → agentic layer; same file) — chunk-level attribution needed for C2.

<!-- lore:01a1d855-dfe6-7f32-a0e5-1df19996d306 -->
* **copier-cat composition engine: one 5-stage pipeline, per-format adapters**: copier-cat composition architecture: ONE process for every file type with small format-specific adapters — neither a universal merge algorithm nor per-format systems. Shared 5-stage pipeline: PARSE (format-specific) → IDENTIFY chunks (shared) → MERGE by identity + ordering (shared) → REPORT every decision (shared) → SERIALIZE once (format-specific). Structured formats (TOML/YAML/JSON) are trees: chunks by path, additive across paths, explicit rule on same-path collision; arrays need identity rules (e.g. \`id\`) or append/replace/dedupe diverge. Markdown: named regions \`\<!-- cc:begin name -->\`…\`\<!-- cc:end name -->\` (heading-path IDs less reliable). Plain text: whole-file replace / ordered concatenation / line merge (.gitignore = ordered line set); arbitrary text may be uncomposable (\`enable\_feature false\` vs \`true\`) — no reliable identity → whole-file ownership or review, never an invented merge; unsupported overlap fails visibly, never silently picks a winner. Binary: never text-merge. Two tiers: structured files join the clean data path; a layer shipping a literal fragment (APT's mise.toml today) works standalone but can't join tier one — converting it is the main migration cost.

Tests: test\_toml\_named\_lists\_merge\_by\_name, test\_yaml\_named\_lists\_merge\_by\_name, Registry(mergers=(TomlMerger(), YamlMerger())). Related copier gotcha (probe-verified 2026-11-13): \`copier -d 'tools={...}'\` replaces the ENTIRE variable value, silently wiping sibling keys (defaults' roborev vanished while the unoverridden \`tasks\` survived) — it reads as a per-key patch but isn't. CC-7 therefore composes structured render results from isolated native renders instead of merging data pre-render; APT's CLI deep-merges TOML properly, so the loss is specific to raw copier -d.

* **copier-cat PRINCIPLES.md consent boundary: --yes scopes, writes need consent at the action**: copier-cat PRINCIPLES.md (constitution): deterministic machinery first; AI may classify and propose but is never the merge engine; all output reviewable; no project modification, overwrite, publication, or source-template patch lands without explicit human consent AT the action. ccc init: automation never prompts, and missing config never selects a default stack; never force-reset or directly edit managed OpenCode config. Assembly spec: \`--yes\` approves ONLY the displayed new-destination write — not agent installation, source-template changes, publishing, telemetry, or updates to an existing project; cancellation leaves no approved destination. Planning/inspection/preview may run automatically; consequential actions need explicit review at the action — a conversational request is not blanket permission for unrelated writes. * **copier-cat scope: single-template copier workflows never need it; stacks only**: A single Copier template is self-describing (questions, files, answers file), so \`copier copy\`/\`copier update\` work with zero copier-cat involvement forever — the lock-in guarantee holds. copier-cat exists ONLY for the stack case: two templates rendering to one destination and claiming the same file (e.g. python-project-template + agentic-project-template both claiming mise.toml). Copier itself has no concept of two templates owning one file — a missing concept in the problem space, not a missing copier-cat feature. Adding copier-cat to single-template flows solves a non-problem. Design thread: \[\[01a1d13b-c05f-7589-a7af-a2d3fe1ba079]].
